# 2026-07-27 : 정방향/역방향 속도 비대칭 — 양방향 정렬 + 지연 보상

| loop | 정방향 | 역방향 |
|---|---|---|

## 1. 양방향 정렬

### 바꾼 것

d축에 전압을 걸고 1초 기다리던 것을, **전기각을 0 → 2π → 0 으로 왕복 스윕**하고
양 끝에서 기계각을 재는 방식으로 바꿨다. 두 오프셋을 단위벡터로 평균낸다.

양 끝은 둘 다 전기각 0 지점이라(정방향 끝은 2π ≡ 0) `offset = -기계각 × 극쌍수` 가
양쪽에 똑같이 성립한다. 끝점 각도는 16샘플 단위벡터 평균으로 잡는다.

- `main.c` : `align_rotor()`, `read_angle_avg()`
- `foc.c` : `foc_align(angle_fwd, angle_rev)`

### 실측

```
FOC: 정렬 오프셋 -109.9도 (정방향/역방향 편차 -1.7도)
```

| | 이전 (단방향) | 지금 (왕복) |
|---|---|---|
| 정방향 250Hz | +45 | **+32** |
| 역방향 250Hz | **−14** | **−42** |
| 정방향/역방향 차 | 31 | **10** |
| 부팅 재현성 | 217.8 / 311.9 / 326.9° 제각각 | **−109.9° 근처 반복** |

전 구간 엔코더실패 0, MPU실패 0, 손상 0. 최대변화도 정 7.7° / 역 10.0° 로
비가 1.30 — 속도비 1.31 과 일치한다. 값이 틀린 게 아니라 진짜 속도차다.

### ★ 원인 정정 : 코깅이 아니라 정지마찰이었다

노이즈 일지에는 원인을 **코깅 편향**으로 적었다. 진행 방향에 따라 코깅이 회전자를
붙잡는 방향이 반대라, 한 방향에서만 재면 그 편향이 오프셋에 남는다는 설명이었다.

**측정된 정방향/역방향 편차가 −1.7° 뿐이다.** 코깅 몫은 그 절반인 0.85°(전기각)다.
0.85° 로 31 rad/s 의 비대칭이 나올 수는 없다. 처방은 맞았지만 이유가 틀렸다.

실제로 고쳐진 것:

```
예전 : 임의 위치에서 ud 인가 → 1초 대기
       회전자가 가장 가까운 안정점으로 끌려가지만 정지마찰 때문에 끝까지 안 간다.
       남은 오차 몇 도(기계각)가 ×7 되어 전기각 수십 도가 된다.
       시작 위치가 매번 달라 잔류 오차도 매번 다르다 → 부팅마다 값이 바뀐다.

지금 : 전기 1회전을 끌고 지나간다
       정지마찰이 깨지고 회전자가 자계를 실제로 추종한다.
```

부팅 재현성이 같이 해결된 것이 이 설명의 근거다. 코깅 편향이라면 회전자가 멈추는
자리에 따라 값이 계속 달라져야 하는데, 왕복 스윕을 넣자 −109.9° 로 고정됐다.

## 2. 커뮤테이션 지연 보상

### 왜 필요한가

엔코더를 읽고 전압 벡터를 내보낸 뒤 다음 갱신까지 회전자는 계속 돈다.
자계가 회전자보다 한 루프치 뒤에 선다.

```
지연[전기각] = 휠속도 × 극쌍수 × 루프주기
```

토크는 자계가 회전자보다 90° 앞설 때 최대다. 지연은 그만큼을 깎는다.

| loop | 속도 | 지연 | 유효 토크각 | sin |
|---|---|---|---|---|
| 999Hz | 46 rad/s | 18° | 72° | 0.95 |
| 250Hz | 37 rad/s | **59°** | **31°** | **0.52** |

### 바꾼 것

읽은 각도가 아니라 **다음 갱신 시점의 예상 위치**에 자계를 세운다.

```c
float adv = LAG_COMP * wheel_vel * dt;
foc_apply_torque(dir * TEST_UQ, angle + adv, offset);
```

`LAG_COMP 1.0` = 한 루프치. `wheel_vel` 이 튀어도 벡터가 날아가지 않도록
`ENC_MAX_VEL × dt` 로 상한을 둔다. `0.0` 이면 보상 없음이라 A/B 비교가 된다.

### 실측

정방향/역방향 차 **10 → 최대 5 rad/s**. 손상 0 유지, 타격음 없음.
(이 판에서는 절대 속도값을 기록하지 않았다. §4 에 있다.)

## 4. 로그 출력 태스크 분리

`ESP_LOGI` 는 UART 송신 버퍼가 빌 때까지 CPU 가 제자리에서 기다린다(폴링).
190자 @115200 = 16.5ms. 이 기다림이 **제어 루프와 같은 태스크 안**에 있어서
그동안 커뮤테이션이 멈췄다. 40 rad/s 면 전기각 175° 진행 = 토크 반전.

제어 루프를 우선순위 10 태스크로 떼어내고, `app_main`(우선순위 1)이 로그를 맡는다.
통계는 길이 1 큐에 `xQueueOverwrite` 로 넘긴다 — 제어 루프는 어떤 경우에도 대기하지 않는다.

**코어는 안 나눴다.** 우선순위가 높으면 로그 태스크가 UART 를 기다리는 중이어도
제어 태스크가 즉시 뺏어온다. 코어 분리가 필요해지는 것은 우선순위로 밀어낼 수 없는
Wi-Fi 인터럽트가 붙을 때다.

### 실측

| | 정방향 | 역방향 | 차 |
|---|---|---|---|
| 250Hz | **+43** | **−42** | **1** |

999Hz 기준선(45~47)을 거의 회복했다. 최대변화도 정방향 10.3° / 역방향 10.0° 로
비가 1.03, 속도비 43/42 = 1.02 와 일치한다. 로그 출력 순간의 토크 충격은 사라졌다.

### 곁가지 : 지연 보상이 정렬 오차를 실제로 흡수한다

이 판의 정렬값이 이전 판과 달랐다.

| 부팅 | 오프셋 | 정방향/역방향 편차 |
|---|---|---|
| 이전 | −109.9° | −1.7° |
| 이번 | **−97.1°** | **+6.3°** |

13° 나 차이 나는데도 속도는 대칭이었다. 지연 보상 전이라면 이 정도 오차가 3.2배
비대칭을 만들었다. **동작점이 `sin` 이 평평한 90° 근처로 옮겨져 정렬 오차에 둔감해진 것**이
숫자로 확인됐다. 정렬 재현성이 완벽하지 않아도 되는 이유다.

## 3. 999Hz 대칭은 정렬이 맞다는 근거가 아니었다

노이즈 일지는 999Hz 에서 +45/−47 로 대칭인 것을 정렬이 정상이라는 근거로 읽었다.
**틀렸다.**

지연만으로는 비대칭이 안 생긴다. 양방향을 똑같이 깎기 때문이다.
비대칭이 나오려면 남은 오프셋 오차 ε 가 있어야 하고, ε 는 한 방향엔 더해지고
반대 방향엔 빠진다.

```
정방향 유효 토크각 = 90° − 지연 + ε
역방향 유효 토크각 = 90° − 지연 − ε
```

999Hz 에서는 지연이 18° 라 동작점이 72°, `sin` 이 평평한 구간이다. ε 가 몇 도 있어도
속도차가 거의 안 난다. 250Hz 에서는 동작점이 31° 로 `sin` 이 가파른 구간에 들어가
같은 ε 가 크게 증폭된다.

**즉 999Hz 대칭은 ε=0 의 증거가 아니라 ε 가 묻힌 상태였다.**
어떤 조건에서 증상이 안 보이는 것과 원인이 없는 것은 다르다.

같은 이유로 지연 보상은 두 가지를 동시에 해결한다.
동작점을 90° 근처로 되돌리면 (a) 양방향 속도가 올라가고
(b) `sin` 이 평평해져 남은 ε 의 영향이 저절로 묻힌다.
ε 를 직접 0 으로 깎는 것보다 확실하다.

## 남은 일

1. 3단계(밸런싱 제어), 4단계(텔레메트리)
2. **Wi-Fi 코어 고정이 안 먹고 있다.** `sdkconfig.defaults:8` 의
   `CONFIG_ESP_WIFI_TASK_PINNED_TO_CORE_1=y` 가 빌드 경고 `unknown kconfig symbol` 로
   무시된다. Wi-Fi 드라이버 태스크가 기본값인 **코어 0**(제어 코어)에 남아 있다.
   바로 아래 `LWIP_TCPIP_TASK_AFFINITY_CPU1` 은 정상 적용됐다. 텔레메트리 붙일 때 처리
3. `dt최대` 를 로그 줄에 추가 — 루프 주기 흔들림을 직접 보려면 필요하다
4. 문서·주석의 "MPU6050" → MPU6500 정정 (`WHO_AM_I = 0x70`)

밸런싱은 저속(수 rad/s)에서 돌기 때문에 지연이 전기각 5° 수준이다.
지금 잡은 비대칭은 고속 전용 현상이라 3단계에서는 거의 안 나타난다.
