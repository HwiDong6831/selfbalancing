## 1. 3D 자세 뷰

대시보드에 로봇의 현재 자세를 3D 로 띄웠다. 디버깅보다는 **보여주기 목적**이다.

### 필요한 데이터는 이미 오고 있었다

펌웨어도 서버도 고칠 필요가 없었다. 대시보드가 받는 프레임에 이미 다 들어 있다.

| 값 | 내용 |
|---|---|
| `balance.angle` | 몸 기울기 [도], 0 = 똑바로 |
| `encoder.angle` | 휠 각도 [도] |

### 진짜 3D 자세는 만들 수 없다

물체가 어느 방향을 보고 있는지는 축 3개로 정해지는데, 이 로봇에서 측정되는 건 사실상
1개다.

- **앞뒤 기울기** — 측정된다. 제어가 쓰는 그 값이다.
- **좌우 기울기** — 가속도 3축이 있어 계산은 되지만, 반작용휠 로봇은 이 축으로 움직일 일이
  거의 없다.
- **제자리 돌기(방향)** — **측정 수단이 없다.** 중력은 "아래가 어디인가" 만 알려주므로 세 축
  중 둘까지만 고정된다. 나머지 하나를 알려면 지자기 센서가 필요한데 없고, 자이로를 적분하면
  몇 분 만에 오차가 쌓여 화면이 제멋대로 돌아간다.

그래서 정확히 말하면 "3D 공간에 로봇 모형을 놓고 **측정된 기울기와 휠 회전을 반영한다**" 다.
눈에 보이는 움직임은 두 개다. 구현의 한계가 아니라 이 로봇의 실제 자유도가 그렇다.

### 어떻게 그릴까 — CSS 냐 3D 엔진이냐

- **A안 CSS 3D 변환:** 라이브러리 없이 상자 몇 개를 회전시킨다. 30~40줄이면 된다.
- **B안 Three.js(채택):** 진짜 3D 엔진. 실물 CAD 모델을 그대로 띄울 수 있다.

자유도가 1~2개뿐이라 처음엔 A안을 권했다. **뒤집힌 이유는 실물 OBJ 모델이 있었기
때문이다**(`docs/frame/obj/`). 보여주기가 목적인데 실물과 똑같은 모형이 움직이는 것과
상자로 흉내 낸 것은 차이가 크다.

### 모델이 마침 우리가 원하는 대로 나뉘어 있었다

| | 정점 | 면 | 범위 (mm) |
|---|---|---|---|
| `Assembly.obj` | 9,126 | 18,384 | X ±86.7 / Y −100.3~73.2 / Z 0~46 |
| `wheel.obj` | 9,848 | 19,856 | X ±64 / Y ±64 / Z 0~4 |

`Assembly.obj` 안에 휠이 들어 있으면 따로 못 돌린다. **정점 수가 휠 하나보다도 적어서**
(9,126 < 9,848) 안 들어 있다는 걸 알 수 있었다.

그리고 **두 모델의 회전축이 똑같이 Z축이다.** 반작용휠은 몸이 기우는 축과 같은 축으로 도니
당연한데, 덕분에 구현이 깔끔해졌다. **몸통 그룹 안에 휠을 자식으로 넣으면** 기울기는 휠이
저절로 따라오고 휠 회전만 따로 주면 된다. 실제 물리와 같은 구조다.

회전 중심은 꼬리 끝(바닥 접점)에 뒀다. 실제로 그 점을 축으로 넘어지기 때문이다.

### glTF 로 바꿨지만 크기는 안 줄었다

OBJ 는 글자로 된 형식이라 브라우저가 읽으려면 일일이 해석해야 한다. 이진 형식인 glTF 로
바꾸면 작아지고 빨라질 거라 봤는데, **3.1MB → 2.9MB 로 거의 그대로였다.**

원인은 이 모델이 면마다 법선(면이 향하는 방향) 을 따로 갖고 있어 **정점을 공유할 수 없기**
때문이다. 면 하나당 정점 3개를 통째로 저장해야 하니 줄어들 여지가 없다.

다만 결과에는 영향이 없다. localhost 에서 받으므로 전송 시간이 사실상 0 이고, 글자 해석이
사라진 것만으로도 실제 로딩은 훨씬 빠르다. **패널을 접어 두고 펼칠 때 읽도록** 해서 첫
화면 로딩에도 얹히지 않는다.

### 부호는 실기에서 확인했다

기울기와 휠 회전 둘 다 처음에 반대로 돌았다. 화면을 보고 부호를 뒤집었다. 휠의 장착 위치도
가운데로 뒀다가 옆판 안쪽으로 옮겼다. 이런 건 계산으로 맞히려 하지 않는 편이 빠르다.

### 축과 각도 표시

수직 기준선(회색)과 로봇 축(주황)을 함께 그리고, 두 축 사이에 호를 그려 벌어진 각도를
보이게 했다. 각도 숫자는 3D 좌표를 화면 좌표로 투영해 HTML 로 띄운다 — 라이브러리를 더
넣지 않고도 확대했을 때 글자가 또렷하다.

## 2. 곁다리로 잡은 버그 — 지우기 버튼이 안 먹었다

시리얼 로그의 "지우기" 버튼이 눌러도 아무 일도 안 했다. 원인은 접기 패널과 관련된 코드였다.

접을 수 있는 섹션의 제목 줄에 버튼을 두면, 버튼을 눌렀을 때 섹션도 같이 접힌다. 그걸 막는
코드가 이랬다.

```js
el.onclick = (e) => e.stopPropagation();
```

**`onclick` 에 대입하면 앞서 걸어 둔 동작이 통째로 덮인다.** 지우기 버튼은 이 줄 때문에
"섹션 안 접히게 하기" 만 하는 버튼이 돼 있었다. 결함 주입의 "전체 해제" 버튼도 같은 이유로
죽어 있었다.

`addEventListener` 로 바꾸니 둘 다 살아났다. 여러 동작을 겹쳐 걸 수 있기 때문이다.

## 3. 코드 완성본 정리

기능이 자리를 잡았으므로 코드를 정리했다.

### 주석 350줄 → 74줄

남긴 기준은 둘뿐이다. **변수가 뭘 뜻하는지**(주로 단위), **함수가 무슨 기능인지**. 각각 한
줄이다.

지운 것은 실측 수치, 날짜, 일지 참조, 왜 그렇게 했는지의 경위, 대안 비교, 함수 안의 설명
주석이다. 이 근거들은 대부분 이미 일지에 있다 — PWM 주파수 선정(07-26, 07-27), 엔코더 손상
판정(07-27, 08-02), WiFi 송신 출력(07-30), 영점 처리(08-02).

### 디버깅용 코드와 조건부 분기 제거

| 지운 것 | 무엇이었나 |
|---|---|
| `DRIVE_MOTOR` 분기 | 0 으로 두면 드라이버를 끄고 계산만 하던 안전 스위치 |
| `USE_TELEMETRY` 분기 | 0 으로 두면 WiFi 없이 시리얼만 쓰던 스위치 |
| `balance_control` | `#if 0` 으로 막아 둔 옛 속도모드 제어 |
| `foc_closeloop_velocity` | `#if 0` 으로 막아 둔 옛 클로즈루프 속도 제어 |
| `foc_openloop_velocity` | 초기 브링업용 오픈루프 구동. 이제 안 쓴다 |
| `mpu6050_read_accel` | 가속도만 읽던 함수. 지금은 가속도+자이로를 한 번에 읽는다 |
| `encoder_get_z`, Z 인터럽트 | 한 바퀴 카운트(CPR)가 맞는지 검증하던 진단. 확정돼 역할이 끝났다 |
| 통계의 `d_max` / `d_max_span` | 엔코더 손상 조사용 계측. 원인이 밝혀져 역할이 끝났다 |
| 옛 PID 상수들 | 위 함수들이 쓰던 값 |

**`DRIVE_MOTOR` 이 사라진 건 짚어 둘 만하다.** 이 스위치는 게인이나 부호를 고친 뒤 모터를
물리기 전에 로그부터 확인하는 안전 장치였다(2026-07-28 일지의 3-A 단계). 이제 부팅하면
**항상 모터가 돈다.** 제어를 다시 손볼 일이 생기면 이 단계를 임시로 되살리는 편이 안전하다.

남긴 것도 있다.

- **엔코더 손상값을 버리는 처리**(`enc_implausible`) — 진단이 아니라 실제 보호 장치다.
  잘못된 값이 커뮤테이션을 날려 급가속시킨 적이 있다(2026-07-29)
- **손상 버린 횟수와 MPU 읽기 실패율** — 계속 봐야 하는 건강 지표다
- **결함 주입** — 검증 기능이지 디버깅 잔재가 아니다
