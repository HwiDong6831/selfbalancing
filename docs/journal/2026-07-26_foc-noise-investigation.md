## 증상

밸런싱 구동 중 모터에서 **"탁탁탁" 타격음과 진동**. 밸런싱이 잠시 버티다 넘어지는 것과
같이 나타났으나, 추적 결과 **두 증상은 별개**로 보인다(소음은 고정 uq 로 돌려도 난다).

- 정지 상태(전류 O, 회전 X): **무음**
- 관성 코스팅(전류 X, 회전 O): **무음**
- 전원 끄고 손회전: **무음**
- **역방향(uq<0)에서 훨씬 심하다**

## 확정된 실험 행렬 ★ 가장 중요

| 조건 | 커뮤테이션 | uq | loop | 결과 |
|---|---|---|---|---|
| 오픈루프, 80 rad/s | 내부 적분 | 고정 | 999Hz | **무음** |
| 고정토크, 47 rad/s | **엔코더** | 고정 | 999Hz | **무음** |
| 고정토크, 37 rad/s | **엔코더** | 고정 | **235Hz** | **소음 (역방향)** |
| 밸런싱 | 엔코더 | 제어기 | 235Hz | 소음 |

**2행과 3행의 코드 차이는 "루프에서 MPU 를 읽느냐" 하나뿐이다.** 그런데 그게 두 가지를
동시에 바꾼다:

- **(a) 루프 주기** 999Hz → 235Hz. 커뮤테이션 지연이 전기각 15° → **63°**
  (`전기각속도 = 휠속도 × 극쌍수 7`, 37 rad/s → 259 rad/s, × 4.25ms = 1.10rad)
- **(b) I2C 버스** 엔코더 단독 → mux 전환 + MPU 트랜잭션이 끼어듦

같이 딸려온 미해석 데이터:

```
999Hz : 튐 0,    최대변화 5.3°
235Hz : 튐 다수, 최대변화 최대 178°
```

**MPU 가 버스에 끼어드는 순간 엔코더 데이터 품질이 무너진다.**

| 가설 | 검증 방법 | 결과 |
|---|---|---|
| 루프 주기 부족(120Hz) | 센서 읽기 축소 → 240Hz | ✗ 변화 없음 |

| 엔코더 값 손상 | 이상값 필터 + 외삽 대체 | ✗ |

### 부분 성공: 정렬 오차 ε

**정/역 최고 속도 비대칭은 해결됐다.** 소음은 남았다.

- 원인: 단방향 정렬은 코깅 디텐트가 회전자를 붙잡는 편향을 그대로 오프셋에 남긴다.
- 실측 **정/역 편차 12.6° 전기각** → 기존 단방향 정렬은 약 6.3° 틀어져 있었다.
- ε 이 있으면 uq 부호에 따라 d축 성분 부호가 뒤집혀(약계자/증자) 한 방향만 속도가 안 붙는다.
- 해결: 전기각 0→2π→0 왕복 스윕 후 양 끝 오프셋을 단위벡터 평균 (`foc_align`).

## 남은 가설

### A. MPU I2C 타임아웃으로 루프가 간헐 정지 (가장 유력)

```c
mpu6050_read_accel_gyro(MUX_CHANNELS[0], ...);   // 반환값을 무시하고 있다
```

`I2C_TIMEOUT_MS = 10`. 읽기가 타임아웃하면 루프가 10ms 멈추고 그동안 **전기각이 얼어붙는다** → 탁.

`최대변화 178°` 도 손상이 아니라 **긴 정지 뒤의 정상 회전**일 수 있다:
`37 rad/s × 85ms = 3.1rad = 178°` (`angle_delta` 가 ±180° 로 접는다).

평균 235Hz 는 유지되면서도 초당 몇 번의 큰 정지는 숨을 수 있다.
**현재 코드에 최악 루프 시간(`dt_max`) 계측이 없다.**

### B. mux 채널이 열린 채로 엔코더를 읽는다

`mux_select()` 후 채널이 계속 열려 있어 하위 MPU 가 버스에 매달린 상태로 MT6701 을 읽는다.

덧붙여 **MT6701 의 주소 0x06 은 I2C 예약 대역(0x00~0x07)** 이다. 0x04~0x07 은 규격상
Hs-mode 마스터 코드라 버스의 다른 장치가 다르게 해석할 여지가 있다. 엔코더 단독일 땐
멀쩡하다가 mux/MPU 가 붙으면 나빠지는 정황과 맞는다.

### C. 내부 풀업만 사용

```c
.sda_pullup_en = true,   // ESP32 내부 풀업 ≈ 45kΩ
```

I2C 표준은 2.2k~10k. 45kΩ 는 매우 약해 배선·정전용량이 늘면 상승 시간이 규격을 벗어난다.
하드웨어 변경 없이는 직접 못 고치지만, `I2C_FREQ_HZ` 를 **낮춰서**(50kHz) 나아지면
신호 품질 문제라는 간접 증거가 된다.

### D. 움찔거림이 `LAG_COMP` 때문일 가능성

역방향에서 회전 없이 움찔거리기만 하는 증상. `LAG_COMP` 도입 후 나타났고 교착 버그를
고친 뒤에도 남았다. **보상 자체가 원인인지 미확인.**

## 다음 테스트 (여기서 재개)

### 0. `LAG_COMP = 0` — 가장 쌈

움찔거림이 내가 넣은 보상 때문인지 원래 있던 건지부터 가른다. 증상이 두 개인데 하나가
인공물이면 판단이 흐려진다.

### 1. 루프 주기 vs 버스 트래픽 분리 ★ 핵심

**MPU 읽기 대신 순수 지연**을 넣어 999Hz 를 235Hz 로 낮춘다. I2C 트래픽은 엔코더만 남는다.

```c
esp_rom_delay_us(3250);   // MPU 읽기 자리에
```

| 결과 | 결론 |
|---|---|
| 소음 발생 | **(a) 루프 주기**가 원인. 지연 보상이 왜 안 들었는지 재검토 |
| 무음 유지 | **(b) I2C 버스 트래픽**이 원인. A/B/C 로 진행 |

999Hz 가 조용했다는 사실이 있으므로 반드시 한쪽으로 갈린다. **정보량이 가장 크다.**

### 2. 계측 보강 (flash 왕복 절약을 위해 1과 같이)

- **최악 루프 시간 `dt_max`** ← 정지를 직접 잡는다
- **8ms 초과 루프 횟수** ← 정지 빈도
- **MPU 읽기 실패 횟수** ← 지금 무시 중인 반환값
- 엔코더 실패/튐/최대변화 (기존 유지)

`dt_max` 가 20ms 이상 찍히고 MPU 실패가 세어지면 **A 확정**.

### 3. 원인별 대응

- **A** → `I2C_TIMEOUT_MS` 축소, 실패 시 이전값 유지, `I2C_FREQ_HZ` 400kHz
- **B** → 엔코더 읽기 전 mux 닫기(0x00 기록). 소프트웨어만으로 검증 가능
- **C** → `I2C_FREQ_HZ` 를 50kHz 로 낮춰 나아지는지 확인

### 4. 소음과 무관하게 확실한 개선

- `I2C_FREQ_HZ` 100k → **400k** (MPU6050·TCA9548A·MT6701 모두 지원). 14바이트 전송 1.5ms → 0.38ms
- `MUX_SETTLE_US` 500 → 150 (실측으로 하한 탐색)
- → 루프 235Hz → 500Hz 이상 기대. **MPU 읽기 하나가 루프의 76%(3.25ms)를 먹고 있다.**

## 테스트 설계에서 틀린 것들 (반복 방지)

1. **오픈루프 테스트가 두 변수를 동시에 바꿨다** — 커뮤테이션 소스뿐 아니라 uq 도 고정으로
   바뀌었다. 뒤늦게 `MODE_TORQUE`(uq 만 고정)로 대조군을 다시 만들었다.
2. **`MODE_TORQUE` 초판도 두 변수를 바꿨다** — MPU 를 안 읽어 루프가 999Hz 로 올라갔다.
   밸런싱 루프 안에서 uq 한 줄만 바꾸는 형태로 고쳤다.
3. **"손회전 무음 → 기계적 원인 배제"는 속도를 통제하지 못했다** — 기계적 힘은 대체로 ω² 에
   비례한다. 손회전 0.5회전/초 vs 구동 2.4회전/초는 힘이 23배 차이다. 관성 코스팅
   (회전 유지·전류만 제거)이 올바른 통제였다.
4. **이상값 임계값을 추정치로 만들어 교착을 만들었다** — `limit = wheel_vel × dt × k` 인데
   `wheel_vel` 은 통과된 샘플에서만 갱신된다. 한 번 거부가 시작되면 영원히 거부된다.
   실제로 휠이 23.5 rad/s 를 넘는 순간 전 샘플이 거부돼 전기각이 얼어붙었고,
   손으로 휠을 돌려 얼어붙은 각도 근처를 지나야만 복구됐다.
   **추정치로 그 추정치의 갱신 조건을 판정하면 안 된다. 초기값을 대입해 볼 것.**
5. **소리를 귀로 세는 계측은 신뢰도가 낮았다** — 1.47회/회전 → 1.05회/회전 → 초당 고정 등
   측정마다 결론이 뒤집혔다. 가속 구간에서는 "회전당 횟수"가 정의되지 않는다.

## 미결 (소음과 별개)

- 밸런싱 튜닝 자체: `DEADBAND 0` 테스트, K2 위주 튜닝, 적분항/휠속도항(K3) 미검토
- **휠 속도항(K3) 부재** — 리액션 휠 도립진자는 상태가 셋(기울기·기울기 각속도·**휠 속도**)인데
  둘만 쓴다. 휠이 한 방향으로 가속만 하다 역기전력으로 토크가 고갈된다.
  엔코더로 이미 `wheel_vel` 을 계산하고 있으니 하드웨어는 불필요.
- **토크 예산 미계산** — `중력토크 = m·g·L·sin(θ)` 와 모터 최대토크를 비교한 적이 없다.
  복원 가능 각도가 몇 도인지 모른다. 로봇 질량·무게중심 높이 필요.
- **상보필터 계수가 루프 주기에 종속** — `COMP_ALPHA` 가 고정값 0.98 이라 시정수 `α·dt/(1−α)`
  가 dt 에 비례한다. 루프 주기를 바꾸면 필터 특성이 같이 변해 튜닝이 흔들린다.
  고정 시정수 기준 `α = τ/(τ+dt)` 로 바꿔야 한다.
- `GYRO_LSB_PER_DPS` 가 `balance.c` 에 중복 (mpu6050.h 매크로와 별개)
- 로그 후킹 설치 시점의 좁은 경쟁 구간 (`s_prev_vprintf` 대입 전 NULL 호출 가능)
- `docs/server.md` §10·§12 가 ESP32 연동 전 기준 → 갱신 필요. 송신 주기도 30Hz → 10Hz 로 변경됨
- 이 일지 파일명이 내용과 어긋남: `2026-07-23_balance-tuning-driver-fault.md`
  → `..._battery-sag.md` 로 변경 검토
