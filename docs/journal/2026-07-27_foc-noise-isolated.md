# 2026-07-27 : FOC 커뮤테이션 소음 — 원인 격리 완료

> **상태: 원인 확정.** I2C 통신선에 MPU 트랜잭션이 끼어드는 것이 원인이다.
> 대책은 아직 없다. 이어서 할 때는 §다음 부터 보면 된다.

전날([2026-07-26](2026-07-26_foc-noise-investigation.md)) 추적이 교착에 빠져,
누적된 진단 코드를 전부 걷어내고 **최소 구성부터 하나씩 얹어 올라가는 방식**으로 바꿨다.
그 결과 두 단계 만에 원인이 갈렸다.

---

## 왜 방식을 바꿨나

전날까지 `main.c` 하나에 진단 모드 3개, 계측 변수 10개, 이상값 거부·재시도·예측·탈출구가
전부 얹혀 있었다. 변수가 너무 많아 무엇을 바꿔도 결론이 안 났다.

무엇보다 **기존 실험 행렬이 두 변수를 동시에 바꾸고 있었다.** "루프에서 MPU 를 읽느냐"
하나만 달랐지만, 그게 (a) 루프 주기와 (b) 버스 트래픽을 같이 바꿨다. 이 둘을 가르지
못한 채로 여러 판을 소모했다.

그래서 `main.c` 를 비우고 **최소 폐루프**부터 다시 쌓았다.

## 단계별 결과 ★ 핵심

| 단계 | 구성 | loop | 배수 | 소리 |
|---|---|---|---|---|
| 1 | 엔코더 커뮤테이션 + 고정 uq | 999Hz | 1.0 | **무음** |
| 2-A | 위 + `vTaskDelay` 1→4ms | 250Hz | 1.0 | **무음** |
| 2-B | 1단계 + 루프에서 MPU 읽기 | 247Hz | **4.8~177** | **소음** |

**`배수`** = 그 초의 최대 각도 변화 ÷ (그 순간 `dt` × 휠속도).
물리적으로 가능한 값이면 1.0 이 나오고, 크게 넘으면 엔코더가 틀린 값을 준 것이다.

### 2-A 가 조용한 것이 무엇을 죽였나

**루프 주기(커뮤테이션 갱신 주기)는 원인이 아니다.**

250Hz·45 rad/s 면 한 루프 동안 회전자가 전기각 73° 를 나아간다
(`45 × 극쌍 7 × 4ms`). 전기각 오차가 90° 를 넘으면 구동 토크가 제동 토크로 뒤집히므로
여기서 소리가 날 것으로 예상했으나 **완전히 조용했다.**

전날 세운 "커뮤테이션 지연으로 토크가 반전되어 나는 소리"라는 설명은 **틀렸다.**

### 2-B 가 시끄러운 것이 무엇을 확정했나

2-A 와 **루프 주기가 같다**(250Hz vs 247Hz). 다른 것은 통신선에 mux 전환 + MPU
14바이트 읽기가 끼어드는 것 하나뿐이다. 그것만으로 소리가 났고, 엔코더 값이 무너졌다.

```
2-A  loop 250Hz  최대변화  4.1도 (dt 5.0ms 설명가능  4.1도 =   1.0배)   무음
2-B  loop 250Hz  최대변화 174.7도 (dt 4.0ms 설명가능  6.6도 =  26.6배)   소음
2-B  loop 243Hz  최대변화 111.1도 (dt 4.0ms 설명가능  0.6도 = 177.6배)   소음
```

회전이 눈에 보이게 끊긴다.

## MPU 실패와 엔코더 손상이 같이 움직인다

`MPU실패` 가 0 인 초는 엔코더 손상도 0 이다. **예외가 아직 한 건도 없다.**

전날 로그 10 줄 + 이번 2-B 의 `19377` 줄, 총 11/11.

```
19377  loop 250Hz  MPU실패 0  최대변화 10.3도 (설명가능 11.2도 = 0.9배)
```

엔코더(MT6701)와 MPU 는 서로 다른 부품인데 같이 실패하고 같이 멀쩡하다.
**공통점은 같은 I2C 통신선을 쓴다는 것 하나뿐이다.**

손상 크기가 **45 / 90 / 180도 근처에만 몰리는 것**도 전날과 동일하다.
14비트 각도값의 상위 바이트에서 한 자리가 뒤집히면 정확히 2048 / 4096 / 8192 카운트,
즉 45 / 90 / 180도가 틀어진다.

## 곁가지 발견 : 정/역 속도 비대칭

2-A 에서 드러났다. 소리와는 무관하다.

| | 1단계 (999Hz) | 2-A (250Hz) |
|---|---|---|
| 정방향 | +45 rad/s | +45 rad/s |
| 역방향 | **-47 rad/s** | **-14 rad/s** |

정방향은 그대로인데 역방향만 무너진다. 원인은 **단방향 정렬이 남긴 오프셋 오차**로 본다.
코깅이 회전자를 붙잡는 방향이 진행 방향에 따라 반대라, 한 방향에서만 끌어와 재면
그 편향이 오프셋에 그대로 남는다.

이 오차는 커뮤테이션 지연과 한 방향에서는 더해지고 반대 방향에서는 상쇄된다.
999Hz 에서는 지연이 18° 라 묻혔고 250Hz 에서는 73° 라 드러났다.

전기각을 0→2π→0 으로 왕복 스윕해 양 끝 오프셋을 단위벡터로 평균내면 상쇄된다
(이전에 구현했다가 이번 정리에서 되돌렸다. 실측 정/역 편차 3.4~6.4° 전기각).
**소리와 무관하므로 순서상 나중에 처리한다.**

## 다음

원인이 **버스 공유**로 확정됐으므로, 이제 버스 쪽만 보면 된다.
사용자 요청에 따라 기계·하드웨어 원인은 배제하고 **펌웨어 설정만** 다룬다.

1. **`I2C_FREQ_HZ`(현재 100kHz)를 50kHz 로 낮춰** 손상률 비교. 그다음 400kHz 로도 비교.
   양방향으로 봐야 신호 타이밍 문제인지 결론이 선다
2. `mpu6050.c` 의 `MUX_SETTLE_US`(500), `I2C_TIMEOUT_MS`(10)
3. MT6701 주소가 **0x06** 인데 이는 I2C 예약 대역(`0000 1XX` = Hs-mode 마스터 코드)이다.
   아직 검증하지 않았다. 주소 변경이 가능한지 확인할 가치가 있다
4. 레거시 `driver/i2c.h` 대신 새 `i2c_master` 드라이버 검토
   (레거시를 쓴 이유는 버스가 멈췄을 때 CPU 가 뻗지 않고 타임아웃을 반환하기 때문)

버스 문제가 해결되면 3단계(밸런싱 제어), 4단계(텔레메트리)로 올라간다.

## 계측 방법에 대해

이번에 실제로 결론을 만든 것은 **`배수` 하나**다.

```
최대변화 174.7도 (dt 4.0ms 설명가능 6.6도 = 26.6배)
```

"큰 값이 들어왔다"는 사실만으로는 루프가 멈춰서 실제로 많이 돈 것인지 값이 틀린 것인지
가릴 수 없다. **그 순간의 `dt` 와 휠속도를 같이 기록해 물리적으로 가능한 값과 비교**하니
한 줄로 판정이 됐다. 전날 로그의 `튐 12` 같은 숫자는 이 비교가 없어 몇 판을 헤맸다.
