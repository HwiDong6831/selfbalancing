# 2026-07-25 : ESP32 → 서버 텔레메트리 송신 + 시리얼 로그 미러링 구현

더미 데이터로 검증해 둔 서버·웹에 실제 ESP32 센서값을 연결하고, 시리얼 로그까지 웹에서 보게 만들었다. 설계 의도와 도중에 막힌 지점을 기록한다.

- ESP32가 WiFi STA로 붙어 WebSocket 클라이언트로 `/ws/esp` 에 30Hz 송신.

- `ESP_LOGx` 출력을 가로채 같은 소켓으로 보내 웹 대시보드에서 시리얼 로그 확인 가능. USB 없이 디버깅.

## 설계 결정

### 코어 분리 (core0 제어 / core1 통신)

`app_main` 은 `CONFIG_ESP_MAIN_TASK_AFFINITY_CPU0` 로 core0 고정인데, WiFi 태스크와 lwIP TCP/IP 태스크는 **기본이 core0** 이다. 그대로 두면 1kHz 제어 루프와 CPU를 다툰다.

`sdkconfig.defaults` 에 두 줄 추가:
```
CONFIG_ESP_WIFI_TASK_PINNED_TO_CORE_1=y
CONFIG_LWIP_TCPIP_TASK_AFFINITY_CPU1=y
```

주의: 처음에 `CONFIG_ESP_WIFI_TASK_CORE_ID_1` 로 썼다가 `unknown kconfig symbol` 경고. IDF 5.5 의 실제 심볼명은 `ESP_WIFI_TASK_PINNED_TO_CORE_1`.

**이것만으로는 부족하다.** 전송 호출 자체가 core0(제어 루프)에서 나면 WiFi 드라이버만 core1로 옮겨봐야 소용없다. 그래서 전송 태스크를 만들어 `xTaskCreatePinnedToCore(..., 1)` 로 고정.

### 길이 1 큐 + xQueueOverwrite

제어 루프가 네트워크 I/O로 블록되면 로봇이 넘어진다. 큐 길이를 1로 두고 `xQueueOverwrite` 로 덮어쓰기만 한다.

- 제어 루프 대기 시간 0 (큐가 차 있어도 실패하지 않음).
- 전송이 밀려도 오래된 프레임이 쌓이지 않는다. 최신 것만 살아남음.

### TELEMETRY_ENABLED 컴파일 토글

런타임 `if` 가 아니라 `#define` + `#if` 로 뺀 이유: 0 일 때 제어 루프 기계어가 통신 도입 전과 동일해진다. 밸런싱 튜닝 중 주기 흔들림의 원인 후보에서 통신을 완전히 배제할 수 있다.

### JSON은 snprintf

cJSON을 안 쓴 이유: 프레임 모양이 고정이라 포맷 문자열 하나로 끝난다. 의존성 0, 할당 0.

`isfinite()` 검사를 넣었다. `angle`/`uq` 가 nan 이면 snprintf가 `nan` 을 뱉는데 이건 유효한 JSON이 아니라 **서버가 프레임을 통째로 버린다**. 화면만 조용히 멈추는 형태라 원인 추적이 매우 어렵다.

### 전송 주기는 시간 기준

처음엔 "제어 루프 30 사이클마다" 였는데, 루프 실제 주기가 1kHz가 아니면 송신 레이트가 같이 흔들린다. `esp_timer` 기준 33000us 간격으로 바꿈.

### 로그 미러링 — 후킹은 큐에 넣기만

`esp_log_set_vprintf()` 로 `ESP_LOGx` 를 가로채되, **콜백 안에서는 큐에 복사만** 한다. 시리얼 출력은 그대로 유지.

- 이 콜백은 WiFi·lwIP 내부를 포함한 **아무 태스크에서나** 불린다. 블록하면 안 된다 (`xQueueSend` timeout 0, 넘치면 버림).
- 콜백에서 직접 WS 전송을 하면 **무한 재귀**에 빠진다. 전송이 실패하면 에러 로그를 찍고, 그 로그가 다시 전송을 부른다.
- 같은 이유로 드레인에도 상한(`LOG_DRAIN_MAX`)을 뒀다. 전송이 로그를 유발하면 큐가 계속 다시 채워져 루프를 못 빠져나간다.
- `CONFIG_LOG_VERSION=1` 전제 (한 줄 = 콜백 1회). v2로 올리면 줄이 조각나 이 가정이 깨진다.

**미연결일 때 로그 큐를 비우지 않는다.** 처음엔 `xQueueReset` 으로 비웠는데, 그러면 WS 연결 전에 나오는 센서·모터 초기화 로그가 전부 사라진다. `telemetry_start()` 를 `app_main` 맨 앞에 둔 의미가 없어진다. 큐 길이를 48로 늘리고 쌓아뒀다가 연결 직후 한꺼번에 올린다.

### 한 소켓, 두 종류

로그를 별도 엔드포인트로 빼지 않고 `/ws/esp` 하나로 보낸다. 서버는 `{"log":` 접두사로 가른다.

트리(`readTree`)로 판별하지 않은 이유: 30Hz로 들어오는 텔레메트리를 두 번 파싱하게 된다. 송신 측 포맷을 서버가 쥐고 있으니 접두사 비교로 충분하다.

## 막혔던 지점

### 1. ESP는 WiFi에 붙는데 서버 연결만 실패

```
E transport_ws: Error connecting to host 192.168.0.2:8080
errno=119 (CONNECTION_TIMEOUT)
```

방화벽을 의심했으나 아니었다. 실제 원인은 **서브넷 분리**:

| | IP | 게이트웨이 |
|---|---|---|
| ESP32 (WiFi) | 192.168.45.66 | 192.168.45.1 |
| PC (유선) | 192.168.0.2 | 192.168.0.1 |

판별 방법: PC에서 `tracert 8.8.8.8` 했을 때 hop2가 `118.218.75.1`(ISP 공인망)이었다. PC 공유기가 WiFi 공유기 밑에 물려 있었다면 hop2가 `192.168.45.1` 로 찍혔어야 한다. → 두 장비가 **서로 다른 회선**.

집에 공유기가 2대였고 ESP가 다른 쪽 SSID에 붙어 있었다. 같은 공유기 SSID로 바꾸니 해결.

**교훈: 연결 안 될 때 방화벽부터 보지 말고 양쪽 IP 대역부터 비교할 것.**

### 2. 엔코더 각도가 20267~20625 로 표시

`encoder.c` 의 단위 혼용 버그:
```c
*angle_rad = 360.0f - (float)raw * ((2.0f * M_PI) / 16384);
```
360(도)에서 라디안을 빼고 있었다. 반환값이 353.7~360 이고, 이걸 라디안으로 보고 ×57.2958 하니 20265~20626.

**FOC가 지금까지 멀쩡했던 이유:** `foc_apply_torque` 가 `POLE_PAIRS * (now_angle - align_angle)` 형태로만 쓴다. 두 값에 똑같이 상수 360이 들어가 차분에서 상쇄된다. 그래서 각도를 화면에 표시하기 전까지 드러나지 않았다.

`2π` 로 고쳐도 차분은 동일 → **밸런싱 튜닝값 그대로 유효**.

### 3. 센서값이 0 / −1 로만 보임

프론트가 `fmt(s[k], 0)` — 소수점 0자리였다. 원래 raw int16(±16384) 기준으로 쓴 코드인데 물리단위(g, deg/s)로 바꿔 보내면서 `0.012 g` 가 ` 0` 으로 뭉개졌다. 가속도 3자리 / 각속도 1자리로 분리.

**교훈: 와이어 단위를 바꾸면 표시 자릿수도 같이 봐야 한다.** 데이터는 정상인데 화면만 이상해서 펌웨어를 한참 들여다봤다.

### 4. ESP-IDF 빌드 환경

`export.ps1` 이 py3.14 가상환경을 찾는데 실제 설치된 건 py3.11. 매번 앞에 붙여야 함:
```powershell
$env:IDF_PYTHON_ENV_PATH="C:\Espressif\python_env\idf5.5_py3.11_env"
. C:\Espressif\frameworks\esp-idf-v5.5.4\export.ps1
```

### 5. 빌드는 성공하는데 로그가 안 뜸 — ninja mtime 함정

시리얼 로그를 한 번 되돌렸다가 백업에서 복원했는데, 재플래시·서버 재시작을 해도 로그가 안 떴다.

코드는 다 맞았다. 서버 라우팅은 테스트로 검증했고(`EspIngestHandlerTest`), 서빙되는 `app.js`/`index.html` 도 최신이었다. 문제는 **펌웨어 바이너리에 로그 코드가 아예 없었던 것**.

```
telemetry.c        mtime 11:16:39   ← 복원된 소스
telemetry.c.obj    mtime 11:22:25   ← 기존 오브젝트
```

PowerShell `Copy-Item` 은 원본 파일의 `LastWriteTime` 을 **보존**한다. 백업에서 복원한 소스의 mtime이 기존 오브젝트보다 오래돼서, ninja가 "이미 최신"으로 판단하고 **재컴파일을 건너뛰었다**. 링크는 옛 오브젝트로 수행됐다.

빌드는 `Project build complete` 를 정상 출력하고 바이너리 크기까지 찍었다. 실패 신호가 전혀 없었다.

**판별 방법:** 산출물에서 마커 문자열을 직접 찾는다.
```bash
grep -q '{"log":"' build/esp.bin && echo 있음 || echo 없음
```
`없음` → 컴파일 안 됨. touch 후 재빌드하니 `telemetry.c.obj` 가 다시 컴파일되고 바이너리가 512B 늘었다.

**교훈: 파일을 복사해서 되돌린 뒤에는 "빌드 성공"을 믿지 말고 산출물에 반영됐는지 확인할 것.** 복원 직후 `touch` 하거나 `idf.py fullclean` 하는 게 안전하다.

## 미결

- `voting`/`fault` 는 FR-2(결함 시뮬레이션) 구현 전이라 `ok`/`none` 고정. 스키마만 채운 상태.
- 프레임률·드롭률 실측 안 함. `TELEMETRY_INTERVAL_US` 는 33000(30Hz) 잠정.
- MPU 3개를 매 사이클 전부 읽도록 바꿨다. I2C 트랜잭션이 3배가 되므로 **제어 루프 실주기 재측정 필요**. 밀리면 `I2C_FREQ_HZ` 400kHz 승격 검토 (MPU6050·TCA9548A·MT6701 모두 지원).
- 로그 큐가 넘치면 **최신 줄을 버린다**(`xQueueSend` 실패). 오래된 줄을 버리는 링 방식이 모니터 의미상 맞지만, 후킹 콜백에서 큐를 pop 하려면 버퍼가 더 필요해 보류. 부팅 버스트는 48줄로 커버됨.
- 로그 후킹 설치 시점에 아주 좁은 경쟁 구간이 있다. `s_prev_vprintf = esp_log_set_vprintf(...)` 에서 훅은 함수 진입 즉시 활성화되는데 대입은 반환 후다. 그 사이에 다른 태스크가 로그를 찍으면 NULL 함수 포인터 호출. 실제로 밟은 적은 없다.
- `docs/server.md` 의 §10「ESP32 연동 시 변경점」·§12 미결사항이 아직 연동 전 기준 → 갱신 필요.
