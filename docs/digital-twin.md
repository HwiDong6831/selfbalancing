# 디지털 트윈

모바일 웹에서 로봇의 현재 자세를 실시간 3D로 확인하는 기능.

## 1. 목적

- 실제 기기의 자세를 모바일 화면의 3D 모델에 실시간 반영한다.
- 센서 결함 시뮬레이션 시 자세 변화를 시각적으로 검증하는 도구로 사용한다.
- 기존 모바일 Wi-Fi 제어 기능(FR-6)과 동일한 웹 UI에 통합한다.

## 2. 자세 데이터

### 자세 소스

- Voting 알고리즘을 통과한 융합 기울기.
- 엔코더가 읽은 휠 각도.

### 표현 방식 — 1축 기울기와 휠 회전

**측정 가능한 자유도가 1개다.** 물체가 향한 방향은 축 3개로 정해지는데, 중력은 "아래가 어디인가" 만 알려주므로 그중 둘까지만 고정된다. 나머지 하나(제자리 돌기)를 알려면 지자기 센서가 필요한데 이 로봇에는 없다. 자이로를 적분하면 몇 분 만에 오차가 쌓여 화면이 제멋대로 돌아간다.

그래서 쿼터니언을 쓰지 않는다. 쿼터니언은 세 축을 다 알 때 의미가 있고, 여기서는 채울 수 없는 성분을 지어내는 셈이 된다. 대신 **실제로 측정되는 기울기 1축과 휠 회전**을 보낸다.

반작용휠 로봇은 몸이 기우는 축과 휠이 도는 축이 같다. 그래서 3D 에서 휠을 몸통의 자식으로 두면 기울기는 휠이 저절로 따라오고, 휠 회전만 따로 주면 된다.

### 페이로드

- 기울기 `angle`, 휠 각도 `encoder.angle`. 텔레메트리 프레임에 이미 들어 있어 별도 필드가 필요 없다.
- 송신 주기: 50Hz.

## 3. 통신

- 프로토콜: **WebSocket** (저지연 연속 스트림, HTTP 폴링 대비 적합).
- 경로: **ESP32 → Spring 서버 → 브라우저**. ESP32 는 서버가 아니라 클라이언트다.
- 기존 모바일 제어 채널과 동일한 Wi-Fi 연결 재사용.

> 처음에는 ESP32 가 직접 WebSocket 서버가 되는 안이었으나, ESP32 부담과 동시 접속 수
> 때문에 Spring 서버가 중계하는 구조로 바꿨다. 근거는 [server.md](./server.md) 3장.

## 4. 모바일 3D 렌더

- 웹 기반 렌더링: **Three.js / WebGL**. 앱 설치 불필요.
- 웹 자산 호스팅: **대시보드와 같은 Spring 서버**. ESP32 온보드 flash 미사용.
- 3D 모델: 기존 프레임 export 재사용. `Assembly.obj`(몸통)와 `wheel.obj`(휠)를 각각 `.glb` 로 변환해 쓴다 — 둘이 따로 있어야 휠만 돌릴 수 있다.
- 몸통 그룹을 기울기만큼, 그 자식인 휠을 엔코더 각도만큼 회전시킨다.

## 5. 결함 시뮬레이션 연동

- 트윈 화면에 센서 상태 오버레이: 어느 센서가 faulted 인지, voting 결과 표시.
- 결함 주입 시 자세 흔들림을 3D로 시각 확인 → 검증 도구 역할.

## 6. 구성요소

| 계층 | 구성요소 |
|------|----------|
| ESP32 | WebSocket 클라이언트 (`espressif/esp_websocket_client`) |
| 자세 소스 | voting 통과 융합 기울기 + 엔코더 휠 각도 |
| 서버 | Spring Boot — 중계 + 웹 자산(HTML/JS) 호스팅 |
| 모바일 웹 | Three.js 3D 렌더, WebSocket 클라이언트 |
| 3D 모델 | 프레임 export 를 변환한 `.glb` (몸통 / 휠) |
